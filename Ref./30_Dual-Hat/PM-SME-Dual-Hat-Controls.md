# PM + SME 겸직 통제 & 경험 매핑

## 1. 겸직 위험과 통제 (Technical inference)

| 위험 | 원인 | 통제 | 검증 증거 |
|---|---|---|---|
| 가정이 사실로 굳음 | SME 컨텍스트를 같은 사람이 BRD화 | 컨텍스트 패키지 모든 주장에 `validated/assumed/unknown/conflicting` 표시 | 표시 누락 0건 |
| 자기 검토 | 작성자=검토자 | `/rpi-challenger`로 가정 공격, 다른 참가자 서명 | 검토 로그 |
| 가격 낙관 편향 | 주제 제안자=가격 소유자 | 재무/영업 검토를 일정에 포함, 권장안 표기 유지 | 승인 공백 목록 |
| 역할 침범 | Architect 경향 | 아키텍처 결정은 ADR + Tech 서명 | ADR 서명 |
| 담당자 없는 위험 | 리드 과부하 | 모든 열린 이슈에 담당자·날짜 | 완료 기준 충족 |

## 2. 경험 → 산출물 매핑

| 본인 경험 | 도움이 되는 산출물 | 문장 예시 |
|---|---|---|
| 기능·정책·적용·enforcement를 분리해 검증 | 신뢰도 표시, 수락 기준 | "설정 존재와 enforcement를 별개 항목으로 AC에 둔다" |
| 규제 산업 제한망/감사 요건 | 컨텍스트 패키지의 제약, Lean Canvas 비용·위험 | "Proxy·TLS 검사 환경에서의 동작을 제약으로 명시" |
| Control/Enforcement/Evidence Plane 설계 | 아키텍처 입력, 추적 매트릭스 | "구성요소→요구사항→테스트→증적 연결" |
| Positive/Negative Path 검증 | 테스트 가능한 AC | "허용 동작과 차단 동작을 모두 AC로" |
| Discovery→Change→Rollback→Verification | 구현 계획 구조, P0 정의 | "모든 변경 작업에 롤백과 검증 단계 포함" |

## 3. 소개 문장 (초안)
> "M365 보안 플랫폼 아키텍트로서, PM 트랙에서는 요구사항을 구현·검증 가능성에서 거꾸로 설계하고, SME 트랙에서는 규제·제한망 환경의 제약을 증거와 함께 제공합니다. 설계 산출물을 대신 쓰기보다, 아키텍트가 나중에 던질 질문을 BRD/PRD 단계에서 먼저 닫는 것이 제 기여입니다."
