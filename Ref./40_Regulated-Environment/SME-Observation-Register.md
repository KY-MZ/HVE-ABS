# SME 관찰 사실 등록부 (금융권 프로젝트 경험)

목적: 본인이 실제로 관찰한 "조직 인프라에 의한 Cloud Feature 제한" 사례를 **사실과 해석을 분리해서** 기록하고, [[Restricted-Environment-Strategy]]의 R1~R10에 연결한다.

## 기록 규칙
- 고객명, Tenant ID, 계정, IP, 내부 DNS 이름, 토큰은 쓰지 않는다. `<Customer-A>`, `<ProxyProduct>`, `<InternalIP>` 같은 placeholder만 쓴다.
- 관찰(무엇을 봤는가)과 해석(왜 그렇다고 판단하는가)을 다른 열에 쓴다.
- 증거 유형: 로그, HTTP 오류, HAR, 정책 설정 화면, 패킷, 사용자 증상. 증거가 없으면 `가설`로 표시한다.
- "정상화되었다"는 원인이 아니다. 해소 조건과 근본 원인을 구분한다.

## 작성에 도움이 되는 질문
1. 어떤 Cloud Feature가 막혔는가? 차단 지점은 단말, 프록시, 방화벽, 테넌트 정책, 신원 정책, 내부 승인 절차 중 어디였는가?
2. 막혔다는 것을 어떤 증거로 알았는가? (오류 문구, 로그, 캡처)
3. 어떻게 풀었는가? 정책을 바꿨는가, 예외를 받았는가, 아키텍처를 바꿨는가, 기능을 포기했는가?
4. 승인에 필요했던 근거 문서는 무엇이었고, 누가 승인했는가? (역할만)
5. 풀린 뒤에도 남은 제약이나 운영 부담은 무엇이었는가?

## 승격 규칙
- 이 표의 항목이 채워지면 [[Restricted-Environment-Strategy]]의 해당 R-ID 행에 "Confirmed observation" 열을 추가해 연결한다.
- 문서 근거(Documented)와 관찰이 충돌하면 충돌 자체를 기록하고 `conflicting`으로 표시한다.
