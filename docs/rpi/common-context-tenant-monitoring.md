## 개요

이 문서는 RPI 워크플로의 초기 진입 전에 공통으로 공유해야 하는 비즈니스 요구사항, 사실, 규칙, 제약, 근거를 정리한 문서입니다. 목적은 "테넌트 전반의 사용자 및 애플리케이션 활동을 모니터링하고, 감사 추적성을 확보하며, SoC 관련 업무를 자동화하는 것"을 명확히 정의하는 것입니다.

이 문서는 추후 조사, 계획, 구현, 검토 단계에서 공통 입력으로 재사용할 수 있도록 작성되었습니다.

## 1. 비즈니스 목적

* 테넌트 전체의 사용자 및 애플리케이션 활동을 체계적으로 모니터링한다
* 중요한 이벤트와 변경 내역에 대해 신뢰할 수 있는 감사 추적성을 확보한다
* 보안/컴플라이언스 운영(SoC 관련)에서 수동 검토와 승인 프로세스를 줄인다
* 정책, 규정, 내부 지침을 반영한 운영 흐름을 표준화한다

## 2. 현재 문제 상황

* 현행 운영은 대부분 수동 처리에 의존하고 있다
* 이벤트, 사용 기록, 승인 흐름 간 데이터 불일치가 발생할 수 있다
* 승인 지연으로 인해 운영 지연과 SLA 저하가 발생할 수 있다
* 활동 추적과 증빙 자료 정리가 일관되지 않아 보안/감사 대응이 느리다
* SoC 관련 활동에 필요한 근거를 빠르게 확보할 수 있어야 하는 요구가 있다

## 3. 비즈니스 배경과 기대 효과

* 조직은 사용자와 애플리케이션 활동을 실시간 또는 준실시간으로 추적해야 한다
* 보안, 컴플라이언스, 감사, 운영 지원 목적의 인사이트를 일관되게 제공해야 한다
* 작업량이 많은 운영 프로세스를 자동화하고, 승인 절차를 필요한 경우에만 적용하도록 조정해야 한다
* 결과적으로 운영 지연을 줄이고, 데이터 품질을 높이며, 심사와 보고를 더 신속하게 준비할 수 있어야 한다

## 4. 핵심 사실(Facts)

* 현재 운영은 수동 중심이며, 처리량과 정확성의 병목이 존재한다
* 월간 처리량은 약 2,000건 수준으로 추정된다
* 평균 처리 소요 시간은 약 4일 수준으로 확인되었다
* SLA 달성률은 약 90% 수준으로 보인다
* 데이터 불일치율은 약 12% 수준으로 추정된다
* 타깃 체계는 Microsoft Graph API를 활용하는 방향으로 가정한다
* 조직 규모와 팀 구성은 소규모(2명 이하)로 제한된다
* 주요 목표는 감사 가능성과 운영 자동화를 동시에 달성하는 것이다

## 5. 규칙, 정책, 제약

### 규칙 및 정책

* 개인 데이터는 저장 시 암호화되어야 한다
* 민감한 작업은 2단계 승인 절차를 따라야 한다
* 내부 정책 문서 A와 B를 준수해야 한다
* 감사 추적은 필요한 근거와 로그가 남아 있어야 한다

### 기술 및 운영 제약

* 한 달 내 결과를 내야 한다
* 별도 예산을 확보할 수 없다
* 기존 시스템을 대대적으로 개편하는 방식은 지양한다
* 팀 규모가 작아야 하므로 구현 범위와 복잡도를 제한해야 한다
* Microsoft Graph API를 중심으로 설계해야 한다

### 프로젝트 경계

* 전체 테넌트에서의 활동 모니터링을 기본 범위로 보되, 실제 수집 대상은 세부 범위를 정해야 한다
* "모든 사용자와 애플리케이션"의 정의와 포함 범위는 명확히 확정되어야 한다
* SoC 자동화의 범위는 대시보드, 알림, 보고서 생성, 정책 점검 중 무엇이 포함되는지 정해야 한다

## 6. 이해관계자

* 비즈니스 소유자: 운영 효율성과 감사 대응 속도 향상에 관심이 있다
* 보안/컴플라이언스 담당자: 정책 준수와 감사 근거 확보를 요구한다
* 운영 담당자: 수동 업무 감소와 처리 속도 개선을 원한다
* 개발/엔지니어링 팀: Graph API 기반 데이터 수집 및 자동화 구현을 담당한다
* 승인 권한자: 민감한 작업의 2단계 검토와 승인 책임을 가진다

## 7. 성공 기준

* 사용자 및 애플리케이션 활동에 대한 표준화된 추적이 가능해진다
* 감사 추적성이 향상되고 근거를 빠르게 확보할 수 있다
* 운영 처리 시간이 단축되고 수동 작업이 감소한다
* SLA 달성률이 개선된다
* 데이터 불일치와 누락을 줄일 수 있다
* 보안/컴플라이언스 보고를 자동화할 수 있다

## 8. 범위와 비범위

### 포함 범위

* 테넌트 활동 데이터 수집
* 사용자 및 애플리케이션 이벤트 추적
* 감사 추적성 확보
* SoC 관련 자동화 아이디어 및 최소 구현 범위 정의
* 정책/승인 기준에 맞는 근거 보존

### 비범위 또는 추가 검토 필요 사항

* 기존 시스템 전면 교체
* 조직 전체의 보안 인프라 전면 재설계
* 포괄적인 SOC 운영센터 구축
* 고정된 요구사항 없이 추정되는 자동화 범위 확장

## 9. 근거 및 증거 상태

현재 증거 상태는 초기 단계이며, 아래 항목이 부족합니다.

* 실제 정책 문서 또는 내부 규정 문서의 구체적 인용
* 샘플 로그, 이벤트 데이터, 혹은 운영 기록
* 기존 시스템과 데이터 소스에 대한 상세 스펙
* 사용자/애플리케이션 범위에 대한 명시적 기준
* SoC 자동화의 정확한 KPI와 우선순위 정의

이 문서는 아직 증거가 완전하지 않기 때문에, 이후 RPI 조사 단계에서 실제 데이터와 정책 문서를 확인하는 것이 필요합니다.

## 10. 열린 의사결정 포인트

아래 항목은 다음 단계에서 명확히 정리해야 합니다.

1. 어떤 범위의 사용자와 애플리케이션을 모니터링 대상으로 할지
2. 어떤 이벤트를 보안/감사 추적 대상으로 포함할지
3. SoC 자동화가 보고서 생성만을 의미하는지, 알림/정책 점검까지 포함하는지
4. 민감 이벤트에 대한 승인 기준과 기준 시점을 어떻게 정의할지
5. 현재 데이터 소스를 어떤 방식으로 통합하여 최소 가용 기능(MVP)을 구성할지

## 11. 공통 Context 문장

다음 문장은 RPI 단계에서 공통으로 사용 가능한 핵심 문장입니다.

> 조직은 테넌트 전반의 사용자 및 애플리케이션 활동을 모니터링하여 감사 추적성을 확보하고, 보안/컴플라이언스 운영을 지원하는 자동화를 도입하고자 한다. 이 작업은 수동 운영의 한계를 줄이고, 정책 준수와 업무 효율성을 동시에 개선하는 것을 목표로 하며, Microsoft Graph API 기반의 최소 변경 설계와 소규모 팀 운영 제약을 반영해야 한다.

## 12. 다음 단계 권장사항

* 실제 정책 문서와 내부 규정 문서를 확인하여 규칙을 구체화한다
* 모니터링 대상 범위를 사용자/애플리케이션/이벤트 기준으로 분류한다
* SoC 자동화의 포함 범위를 정의한다
* 데이터 증거와 샘플 로그를 확보해 초기 계획의 신뢰도를 높인다
* RPI 계획 단계에서 MVP 범위와 성공 기준을 더 구체화한다

## 결론

이 문서는 초기 공통 Context로서, 향후 RPI 조사와 계획 단계에서 작업의 방향, 제약, 근거, 열린 질문을 일관되게 공유하는 기준이 됩니다. 현재는 비즈니스 목표와 제약 조건이 비교적 분명하나, 실제 데이터와 정책 근거가 부족한 상태이므로, 이후 단계에서 증거 수집과 범위 확정이 필수입니다.
